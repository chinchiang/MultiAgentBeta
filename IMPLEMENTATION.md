# 實作契約 — 0.2.1

權威驗證依據：backend/vibe_audit/domain.py、contracts.py、policy.py 與 docs/run-input.schema.json（schema 版本 2）。

## API

所有路由皆以 /api 開頭；在已有 session 的情況下，未知的 /api 路徑會回傳 JSON 404。GET /session 會以啟動權杖（X-VibeAudit-Token；以 `#token=…` 形式印在啟動 URL 中，或以 VIBEAUDIT_SESSION_TOKEN 固定）換取 8 小時的 HttpOnly SameSite=Strict session cookie 與 CSRF token。其餘所有 /api 請求（含讀取）都必須同時具備該 cookie 與 X-CSRF-Token：cookie 會送達主機上的每個連接埠，因此僅憑 cookie 無法開啟任何東西，而 GET /session 只會把 token 回傳給已出示該 token 的呼叫方。Host/Origin 檢查涵蓋工作區路由。錯誤格式：{detail: ..., detail_zh?: ...}；`detail` 是固定的英文訊息，`detail_zh` 是 `messages.py` 對照表中的正體中文說法（沒有對照時省略）。run 的 `error` 也同樣附帶 `error_zh`，控制台依介面語言顯示。

| Method | Route | Purpose |
|---|---|---|
| GET | /session, /capabilities | Session/CSRF 與實際設定的 runtime 可用性；/capabilities?profile=… 回報該 runtime profile（預設：default） |
| GET | /messages | 引擎固定訊息的正體中文對照表（`messages.py` 的 `exact`、`status` 與 `patterns`）；控制台以它顯示執行紀錄、缺口、判定說明與示範內容，模型、掃描器、目標與操作者的文字維持原文 |
| GET / PUT | /projects, /projects/{id} | 列出／儲存專案設定 |
| GET / PUT | /models, /models/{id} | 列出／儲存 profile；僅限憑證參照 |
| GET | /catalogs?standard=... | 標準 ID、版本與來源出處 |
| POST | /models/probe | 明確的端點契約，含 policy／預算 |
| GET / POST | /runs | 列出 run 摘要（id、名稱、模式、狀態、階段、時間、用量、錯誤；事件、發現與證據紀錄隨 /runs/{id} 回傳）／建立不可變的 manifest |
| GET | /runs/{id} | 狀態、用量、缺口與發現 |
| POST | /runs/{id}/start, /cancel, /resume | 生命週期轉換；對 awaiting_approval 的 run 呼叫 /cancel 即退回模型設計的案例（狀態改為 cancelled，不送出任何請求；之後 resume 會重新交付審視） |
| POST | /runs/{id}/approve-cases | 操作者核准確切的封存案例集（{receipt}：run 的 gate_receipts.cases），記錄為 operator-attestation 證據後恢復進入黑箱執行 |
| GET | /runs/{id}/events | SSE 進度事件 |
| GET | /runs/{id}/trace | 持久化的實體、連結與歷史 |
| GET | /runs/{id}/evidence/{artifact_id} | 綁定於 run、經雜湊驗證的信封 |
| GET | /runs/{id}/report?format=json or markdown or sarif&lang=en or zh-Hant | 經驗證的匯出；lang 只影響 Markdown 報告的用語（預設 en），JSON 與 SARIF 不變 |
| POST | /runs/{id}/retest | 建立連結到原始發現的新 run（trace 記錄 `retests` 連結，Markdown 與 SARIF 會標註父項）。只複製測試所選發現之威脅的上層案例（所選發現都沒有威脅連結時複製全部）。複測完成後，每個上層發現都會新增一筆 `retests`（pass/fail/inconclusive/untraced）；validated_dynamic 的發現只有在測試其威脅的每個案例都執行且 pass 時，才會變成 resolved_in_retest；之後的複測再次觀測到違規時，會回到 validated_dynamic |
| POST | /runs/{id}/reconcile | 操作者對 worker 清理的證明；關閉處於 cancelling 狀態的 run，該 run 仍不可恢復（unresumable） |
| POST | /runs/{id}/findings/{finding_id}/decision | 以證據為依據的 refuted／inconclusive 決策：被引用的黑箱執行必須測試該發現的威脅（若該發現沒有威脅連結，由操作者命名這些威脅）；要駁回（refute）需要一次 pass，且該 run 中這些威脅沒有任何失敗；validated_dynamic 狀態的發現只能透過已連結的 retest 清除 |
| GET | /openapi.json | 位於 /api/openapi.json 的 OpenAPI schema（需要 session 與 CSRF token；不提供互動式文件頁面） |

Stages（階段）：新 run 在任何工作開始前會先記錄於 `intake` 階段；實際執行的圖為 preflight → whitebox → adjudication → threat_model → case_design → blackbox → report → complete。
Run 狀態：created/awaiting_approval/running/cancelling/cancelled/completed/incomplete/blocked/failed。案例由模型設計的 live run 會在送出任何黑箱請求前停在 awaiting_approval。
Finding（發現）狀態：hypothesis/corroborated_static/validated_dynamic/resolved_in_retest/refuted/inconclusive。
Execution（執行）狀態：pass/fail/inconclusive/blocked/execution_error/outcome_unknown。工具執行完成不代表通過安全性檢驗（security pass）。若 fail 的目標重置或其後的 dispatch 未經確認，該發現會保留並標記 target_state_confirmed=false；與 outcome_unknown 一樣，它會停止 run 並阻止 resume。部署識別變更會停止 run（deployment_changed=true）並阻止 resume；每次排定的重複執行只會送出該 case 一次。模型設計的 case 必須符合嚴格的 case contract，而提供的 case 會在 run 建立時做型別檢查。含 supplied 或 retest case 的 run 會把這些 case 未涵蓋的自動化威脅記錄為 gap；威脅模型必須保留每個此類 case 所測試的威脅 ID。Worker 的結果會由 supervisor 的欄位與記錄重建，因此 worker 回傳的多餘鍵無法設定 verdict、observations 或步驟標籤；不論由哪個 executor 執行 case，每個內容 oracle 都需要一個已驗證的 positive control，且該 control 顯示過每個禁止的 canary。在 resume 時，lease journal 顯示已完成的工作會直接回傳其已記錄且已計費的結果，而非重播或要求 reconciliation；prepared 或 sent 狀態的工作永不重播，並保留其 reconciliation 路徑。

## 模組（Modules）

- service：LangGraph 編排、凍結的 manifest、已封存（sealing）的審查、靜態證據聯集、閘門（gate）、含日誌（journal）的執行／報告。每個模型 payload 都依 512 KiB 上限裁切：超過時，先省略沒有發現引用的最大檔案文字，並記為缺口。各階段經 stage_answers 向模型要回答，續跑沿用與保留的規則在那裡。預算或時間拒絕以原本的原因呈現（blocked），不會變成一般的 provider 失敗。
- answers：`ModelAnswers` 處理一次付費的模型回答。送出前先以 port 的 `check` 拒絕政策不允許的 profile，再預扣保留額度（請求與 system 的位元組數、輸出上限加上固定餘裕），以 port 的 `send` 送出一次，在本機做 JSON、schema 與合約驗證；不合格時再問一次（共 2 次）。每位 Agent 作答結束時，它的用量才計入 run；有代答時，主要 Agent 與備援各自結清。`ask` 處理操作者設定的備援（只在拒答或截斷時），續跑要不要沿用由 stage_answers 決定；`probe` 是預檢的能力探測；`unowned` 給不屬於任何 run 的回答用，帳只存在記憶體，也不記事件：控制台 `/models/probe` 的 `for_probe` 與 benchmark live 模式的每一步都用它。保留額度在每次回答結束時由它結清：成功或已計量的失敗就釋放；取消時把整筆計為已用（`tokens_estimated`）再釋放；用量不明時保留下來並鎖住 `usage_unknown`。呼叫進行中控制器就停掉時，留在儲存裡的保留額度讓重啟檢查鎖住 `usage_unknown` 並記一筆缺口。所以沒有進行中的呼叫時保留額度為 0，唯一的例外是用量不明。每次 schema 重試寫一筆 warning 事件，記下 Agent、階段、第幾次與驗證位置；給模型的重試提示可能帶出模型寫的 id，只放進重試訊息。驗證位置只用 schema 宣告過的欄位名稱，模型自己寫的 key 顯示為 `*`。port 有兩個 adapter：正式的 `providers.LiteLLMPort` 與測試用的 `tests/fakes.py` `FakePort`，以 `Engine(store, model_port=...)` 注入。
- stage_answers：`StageAnswers(run, answers)` 決定一個階段的角色由誰回答，以及答案留不留；付費與驗證仍由 answers 負責。`seat(role)` 是角色的專責 Agent，否則是 commander；可選的 reporter 沒有設定時是 `None`，報告就跳過排序，不退回 commander。`seats("reviewer")` 是三位審查員，各自作答。`answer(角色或 seat, 指示, payload, 合約)` 是 async context manager：區塊裡只放依賴這份答案的檢查，區塊正常結束才保留；區塊丟出例外時，這個名稱底下保留的答案一律清掉，下次續跑重問；取消不算失敗，保留的答案不動。保留的是模型的原始答案，階段拿到的是拷貝；續跑時問題（主要 Agent id、指示與 payload 的雜湊）相同就沿用、不再付費，並重跑檢查。保留名稱：challenger、architecture_mapper、threat_modeler、test_designer 各用角色名，commander 的審查計畫存成 `commander_plan`，reporter 的排序存成 `report_order`；審查員不保留，續跑以 `run["reviews"]` 裡已完成的審查為準。每次回答都回報 `answered_by`，只有白箱記進審查。升級前的 run 保留的答案照樣沿用；只有 `commander_plan`／`report_order` 欄位、沒有對應保留答案的 run，由白箱與報告階段照舊沿用那兩個欄位、不重問。reporter 收到的 finding 摘要依 id 排序，續跑時問題才會相同。
- providers：「送出一次」的 `LiteLLMPort`：`check` 不送出也不花費地拒絕政策不允許的 profile；`send` 經 LiteLLM 與受保護的傳輸送出一次請求，回報用量與結束方式（拒答、截斷）。要不要接受回答、要不要再問，由 answers 決定。另含明確的 origins／憑證（Bedrock 以 VIBEAUDIT_BEDROCK_PROFILES 列出的 AWS profile 簽章，端點限 bedrock-runtime.<region>.amazonaws.com）、providers 本身無 fallback、用量是否可知的判定（依操作者政策，端點實際回應的拒絕（HTTP 400、401、403、404、413、422）、429 與 5xx 視為未處理、未計費，run 仍可恢復；逾時（含 408）與其他失敗維持用量不明）。json_schema 模式送給端點的 schema 不含 maxItems（Gemini API 會以 400 拒絕），回覆仍在本機依完整 schema 驗證。
- staging/snapshot：有界的原始私密掃描器輸入，以及另外去識別化（redacted）的模型情境；儲存庫設定無法控制命令。`unredacted_literals` 列出的確切值（6 到 200 個字元，最多 50 個）是操作者宣告的合成測試憑證：整個值完全相同才不遮蔽，只包含它的值仍會遮蔽；快照的第一項缺口記下有幾個出現在快照裡；與模型金鑰（run 的或環境綁定到模型 origin 的）相同時預檢拒絕。
- request_rules：請求規則與請求計畫，只依賴標準函式庫（後端以套件匯入，supervisor 在容器裡以扁平模組匯入）。
  - `plan_case(manifest, case, *, live, lifecycle=None)` 產生請求計畫：案例本身、正向控制與 fixture 生命週期（`seal_cases` 由 `fixture_protocol.fixture_lifecycle` 傳入；沒傳就讀已封存計畫裡的生命週期步驟，計畫出現之前封存的案例則讀 `allowed_requests`）。規則逐條檢查全部步驟，順序是 header → 身分 → 執行範圍（只在 live）；違反時拋 `RequestRefused`，帶規則代碼（`headers`、`identity`、`scope`）與步驟 id，案例閘門與 `authorize` 以各自的 `*_REFUSALS` 對照表換回原本的訊息，複測預檢依規則代碼自己組成訊息。案例閘門與複測預檢用它；`seal_cases` 在算雜湊之前先拿掉案例帶進來的計畫與 `allowed_requests`，再寫入 `case["request_plan"]`，所以計畫由案例雜湊與操作者的核准涵蓋；違反規則的案例不寫計畫，交給後面的案例閘門以它自己的訊息拒絕。
  - 計畫的每一步有 `id`、`phase`（`case`、`control` 或生命週期的 phase）、`source`、`method`、`path`、`identity`、`headers`、`body`、`read_only` 與 `body_permitted`。`source` 是 model、operator 或 engine：案例不是模型寫的、而且列在 `manifest["cases"]`，才是 operator；header 詞彙、本文規則與會不會改變狀態都看它。生命週期步驟不記本文（instrument 的本文每次重新產生）。引擎步驟的方法、路徑、身分與 header 跟案例本身、正向控制或排在它前面的引擎步驟都相同時，只留前面那一步；所以 header 不同的引擎步驟會跟案例自己的步驟並存。
  - `match_request(manifest, case, request, *, expect=None)`：先檢查執行範圍（`in_scope`），再找計畫裡方法、路徑、身分相同的那一步，拒絕時的代碼是 `scope`、`step` 或 `identity`。有多步時以 `expect`（呼叫端即將送出的封存步驟）的 header 挑選，分不出來就取第一步：計畫把案例本身與正向控制排在引擎步驟前面。`authorize`、supervisor 與 fixture 序列都用它。
  - 其他介面：`own_step(case, manifest=None)` 是案例本身那一步；`read_only(case)` 給 worker 判斷會不會改變狀態；`body_permitted(step)` 說這一步能不能帶本文或是寫入（缺欄位就是不能）；`CASE_PHASES` 是案例本身與正向控制的 phase。controller 從 `own_step` 讀 `side_effects` 與 fixture 案例的本文規則。
  - 舊 run 相容：沒有 `request_plan` 的案例，`match_request` 與 `own_step(case, manifest)` 從它的欄位當場算出計畫（生命週期讀 `allowed_requests`），不檢查規則、不寫回，案例雜湊與核准都不變；worker 拿到沒有計畫的案例時，`read_only` 依 `designed_by` 判斷。
  - 傳輸層的 `adapters._prepare_request` 讀同一套 header、詞彙與路徑規則；允許的方法清單在它、`fixture_protocol` 的 profile 註冊與 `tool_runners` 的工具請求裡各還有一份。
- worker_runtime/worker_entry：controller、獨立且受信任的 supervisor、隔離的 worker 與 Unix socket relay。Docker 沒有直接對外連線（egress）；process_test 明確不隔離，runtime profile 只能選用 Docker 後端。supervisor 從 worker 啟動起以 timeout_seconds 限制 worker；lease 與 controller 的結果期限另涵蓋 supervisor 啟動、有界的容器建立預算與 teardown。supervisor 啟動之後，controller 端的任何失敗都是 outcome_unknown，不會回報「未送出」；worker 回傳格式錯誤時為 execution_error，並保留 supervisor 的紀錄，已記錄的外洩仍判 fail。只有 supervisor 或 controller 能設定的欄位會從 worker 的 JSON 中丟棄。一次轉送請求（從 broker lock 到最後一個位元組）在 9 秒內結束，早於 relay 與工具 client 的 10 秒逾時；目標收到的是封存的 body 位元組。Docker Engine API 版本與 daemon 協商（1.44–1.52）。controller 的結果期限涵蓋 supervisor 有界的容器建立預算加上 teardown，因此緩慢的 daemon 無法為健康的 worker 憑空捏造 unknown 結果。
- supervisor 送出前以 `match_request` 比對請求計畫：先照順序比對 spec 的下一步（`http_case` 與 `request_sequence`），再找出計畫裡的那一步，來源與能不能帶本文都讀那一步；找不到就拒絕。tool 任務只送案例本身與正向控制。`http_case` 的 worker 只拿到計畫裡案例本身那一步，用來判斷會不會改變狀態；`request_sequence` 的 worker 只拿到案例 id 與各步的請求，沒有計畫；tool 任務只跑操作者自填的案例，照原樣拿到 spec。
- lease：持久的 capability 綁定、保留（reservation）帳本、續約／到期、unknown 結果。controller EOF 或到期會在終止前先撤銷 socket。續約在 controller 事件迴圈之外執行；worker guardian 與 controller 心跳可以容忍個別的暫時性 lease 資料庫錯誤（每個 TTL 續約四次；連續兩次失敗仍可容忍，第三次即結束 worker），但遇到真正的到期或撤銷時會立即 fail closed。
- tool_runners：固定的 input／argv 編譯 → 隔離執行 → 有界的 artifact 收集 → 正規化的 observations → 以 broker 證據為本的 oracle。不允許任意的 shell／腳本。
- fixture_protocol：經審查且具雜湊的 reset/setup/cleanup、session 擷取、由管理員註冊的通用 profile；內建者皆為合成。`fixture_lifecycle` 列出引擎加在 fixture 案例前後的步驟（id、phase、方法、路徑、身分與固定的 header，不含本文），封存時寫進請求計畫；序列送出前，每一步都以 `match_request` 比對計畫。
- effect_collector：獨立排序的事件與 sink 收執，以僅在 collector 驗證期間存在的 per-call 金鑰進行 HMAC 綁定（儲存的 bundle 是證據記錄，而非可重新驗證的簽章）；目標的 JSON 無法賦予來源證明（provenance）。
- store/traceability：正式環境用 PostgreSQL、示範用 SQLite、atomic 的 job/run 提交、版本化的實體／證據連結；事件存在自己的 append 表（每次存檔只寫入尚未儲存的事件，run 本體不含事件），進度串流只讀游標之後的事件，`/runs` 清單只讀摘要。
- catalog：釘選的標準 ID、版本／來源檢查；類別歸屬不等於測試涵蓋或認證。
- settings：後端程序的 VIBEAUDIT_* 設定在同一處讀取並檢查（啟動權杖的格式與強度、資料目錄、資料庫 URL、控制台 origins 正規化為瀏覽器送出的形式、來源根目錄、目錄與設定檔路徑）；憑證 reference 不是設定，仍由 adapters／providers／supervisor 依 run 或 profile 給的名稱各自讀取。
- benchmark：七個比較臂（arm）、共用的預算／工具證據、獨立的 ground truth 與不完整項目的計量。合成 run 僅驗證管線本身。

## 角色與證據

Live 模式需要一名 commander 與三個不同的 reviewer 設定／家族。選用的專職 architecture_mapper、challenger、threat_modeler 與 test_designer 可以使用經核准的獨立端點；否則由 commander 扮演這些角色。選用的 fallback Agent 以 `fallback_for` 列出它代替的 Agent：只在那些 Agent 拒答（refusal）或輸出被截斷（truncated）時代答，其他失敗照常停止 run；它和其他模型一樣在預檢探測、計入同一份預算，每次代答都記在活動紀錄與報告的能力限制，審查結果記下實際撰寫的模型（`answered_by`），所以家族多樣性閘門檢查的是它；審查員的備援因此必須是其他審查員沒用的家族，每個 Agent 最多一個備援。報告只驗證既有證據；選用的專職 reporter 只能重新排列確切既有的 finding ID 順序，不能建立新的主張。模型不能新增目標、執行 shell、變更網路政策，也不能以多數決確認發現。

Reviewers 收到相同的核心問題與快照，但不包含掃描器的發現或其他 reviewer 的結論。靜態掃描器可並行執行，但只有在初始批次封存後才會加入。缺少 reviewer 就無法產出完整的三模型審查。

Case 會綁定威脅模型、需求、原始碼、fixture 與 case 的雜湊。Control 與 cleanup 也必須在範圍內。封存的 case 帶著它的請求計畫，由 case 雜湊涵蓋：之後的 `authorize`、supervisor 與 fixture 序列只放行計畫裡的步驟。部署變更需要新的 run；unknown 結果需要 reconciliation/reset。

請參閱 docs/LINUX_SETUP.md、docs/VALIDATION.md 與 docs/DELIVERY.md。

## API

All routes start with /api; with a session, an unknown /api path is a JSON 404. GET /session exchanges the startup token (X-VibeAudit-Token; printed as `#token=…` in the launch URL, or fixed with VIBEAUDIT_SESSION_TOKEN) for an 8-hour HttpOnly SameSite=Strict session cookie and the CSRF token. Every other /api request, reads included, needs both the cookie and X-CSRF-Token: cookies reach every port on the host, so the cookie alone opens nothing, and GET /session returns the token only to a caller that already presents it. Host/Origin checks include workspace routes. Errors: {detail: ..., detail_zh?: ...}; `detail` is the stable English message and `detail_zh` its Traditional Chinese wording from the table in `messages.py` (omitted when there is none). A run's `error` likewise carries `error_zh`; the console shows the one for its language.

| GET | /messages | Traditional Chinese table for the engine's fixed messages (`exact`, `status` and `patterns` from `messages.py`); the console uses it for the activity log, gaps, verdicts and demo content, and leaves model, scanner, target and operator text as written |

Stages: a new run is recorded at stage `intake` before any work; the executed graph is preflight → whitebox → adjudication → threat_model → case_design → blackbox → report → complete.
Run status: created/awaiting_approval/running/cancelling/cancelled/completed/incomplete/blocked/failed. A live run whose cases were designed by a model stops at awaiting_approval before any black-box request.
Finding state: hypothesis/corroborated_static/validated_dynamic/resolved_in_retest/refuted/inconclusive.
Execution state: pass/fail/inconclusive/blocked/execution_error/outcome_unknown. Tool completion does not imply security pass. A fail whose target reset, or a later dispatch, is unconfirmed keeps its finding and carries target_state_confirmed=false; like outcome_unknown it stops the run and blocks resume. A deployment-identity change stops the run (deployment_changed=true) and blocks resume; each scheduled repetition sends the case once. Model-designed cases must match a strict case contract, and supplied cases are type-checked when the run is created. Runs with supplied or retest cases record automated threats those cases leave out as gaps; the threat model must keep every threat ID such a case tests. Worker results are rebuilt from supervisor fields and records, so extra keys a worker returns cannot set a verdict, observations or step labels; every content oracle needs a verified positive control that showed each forbidden canary, whatever executor ran the case. On resume, a task the lease journal shows finished returns its recorded, paid result instead of replaying or demanding reconciliation; prepared or sent tasks are never replayed and keep their reconciliation path.

## Modules

- service: LangGraph orchestration, frozen manifests, sealed reviews, static evidence union, gates, journaled execution/report. Every model payload is fitted to the 512 KiB limit: past it, the largest files no finding cites lose their text first and the omission is a gap. Every stage asks a model through stage_answers, where the rules for keeping and reusing an answer on resume live. A budget or time refusal reaches the run as itself (blocked), not as a generic provider failure.
- answers: `ModelAnswers` handles one paid model answer. Before sending it has the port's `check` refuse a profile the policy denies, then holds a reservation (the request and system bytes, the output limit and a fixed margin), sends once through the port's `send`, and validates the JSON, schema and contract locally; an invalid answer is asked again once (2 attempts in all). An Agent's usage joins the run's when its attempt at the answer ends; with a fallback answer, the primary Agent and the fallback each settle their own. `ask` adds the operator's fallback (on a refusal or truncation only), and whether a resumed stage reuses an answer is for stage_answers to decide; `probe` is the preflight capability probe; `unowned` serves answers that belong to no run, with an account kept only in memory and no event log: the console's `/models/probe` (`for_probe`) and each step of the live benchmark use it. It settles every reservation when the answer ends: a success or a metered failure releases it; a cancellation charges all of it as used (`tokens_estimated`) and then releases it; unknown usage keeps it and latches `usage_unknown`. If the controller stops while a call is in flight, the reservation left in the store makes the restart check latch `usage_unknown` and record a gap. So with no call in flight the reservation is 0, except where usage is unknown. Each schema retry writes one warning event naming the Agent, stage, attempt and validation site; the retry hint, which can quote IDs the model wrote, goes only into the retry message. A validation site names only fields the schema declares; a key the model wrote shows as `*`. The port has two adapters, production `providers.LiteLLMPort` and the test `FakePort` in `tests/fakes.py`, injected with `Engine(store, model_port=...)`.
- stage_answers: `StageAnswers(run, answers)` decides who answers a stage's role and whether the answer is kept; paying for and validating it stays with answers. `seat(role)` is the role's dedicated Agent, or else the commander; the optional reporter, when none is configured, is `None`, and the report skips ordering rather than asking the commander. `seats("reviewer")` is the three reviewers, each answering on its own. `answer(role or seat, instruction, payload, contract)` is an async context manager: its block holds only the checks that depend on the answer, and the answer is kept only if the block ends normally; an exception leaving the block clears whatever is kept under that name, so the next resume asks again; a cancellation is no failure and leaves what is kept. What is kept is the model's own answer and the stage works on a copy; a resumed stage asking the same question (a digest of the primary Agent id, instruction and payload) reuses it unpaid and runs its checks again. Names kept under: challenger, architecture_mapper, threat_modeler and test_designer each under the role's name, the commander's review plan as `commander_plan`, the reporter's order as `report_order`; reviewers keep nothing, and a resume goes by the completed reviews in `run["reviews"]`. Every answer reports `answered_by`, and only the whitebox records it in the review. Answers a run kept before this module existed are still reused; a run with only the `commander_plan` / `report_order` field and no kept answer behind it resumes on that field, unasked, in the whitebox and report stages. The reporter reads the finding summaries in id order, so a resumed stage asks the very question it asked before.
- providers: the send-once `LiteLLMPort`: `check` refuses a profile the policy denies without sending or costing anything; `send` sends one request through LiteLLM and the guarded transport and reports what it cost and how the provider finished (refusal, truncation). Whether an answer is acceptable, and whether to ask again, is for answers to decide. Also explicit origins/credentials (Bedrock signs with an AWS profile listed in VIBEAUDIT_BEDROCK_PROFILES, and its endpoint must be bedrock-runtime.<region>.amazonaws.com), no fallback in providers itself, and whether usage is known (by operator policy, a rejection the endpoint actually returned (HTTP 400, 401, 403, 404, 413, 422), a 429 or a 5xx counts as not served and unbilled, so the run can resume; a timeout (408 included) or any other failure keeps usage unknown). In json_schema mode the schema sent to the endpoint has no maxItems, which Gemini's API refuses with HTTP 400; answers are still validated locally against the full schema.
- staging/snapshot: bounded raw private scanner input and separately redacted model context; repository config cannot control commands. The exact values in `unredacted_literals` (6 to 200 characters, at most 50) are synthetic test credentials the operator declares: only a whole value identical to one stays unredacted, and a value that merely contains one is still redacted; the snapshot's first gap records how many appear in it; preflight refuses one equal to a model key (the run's, or one the environment binds to a model origin).
- request_rules: the request rules and the request plan, standard library only (the backend imports it as a package, the supervisor inside the container as a flat module).
  - `plan_case(manifest, case, *, live, lifecycle=None)` builds the request plan: the case's own request, its positive controls and the fixture lifecycle (`seal_cases` passes `fixture_protocol.fixture_lifecycle`; without it the lifecycle steps of the sealed plan are read, or `allowed_requests` for a case sealed before plans existed). Each rule is checked over every step before the next, headers → identity → run scope (live only); a step that breaks one raises `RequestRefused` with a rule code (`headers`, `identity`, `scope`) and the step id, and the case gate and `authorize` map the code back to their own messages through their `*_REFUSALS` tables, while the retest preflight words its own message from the code. The case gate and the retest preflight use it; before hashing, `seal_cases` drops any plan and `allowed_requests` a case brought along and writes `case["request_plan"]`, so the case hash and the operator's approval cover the plan; a case that breaks a rule gets none, and the case gate after it refuses it in its own words.
  - Each step has `id`, `phase` (`case`, `control` or the lifecycle phase), `source`, `method`, `path`, `identity`, `headers`, `body`, `read_only` and `body_permitted`. `source` is model, operator or engine: a case is the operator's only when the model did not write it and it is listed in `manifest["cases"]`; the header vocabulary, the body rule and whether a step changes state all go by it. Lifecycle steps record no body (the instrument step's is built afresh each repetition). An engine step with the same method, path, identity and headers as the case's own request, a control or an earlier engine step is dropped, so an engine step with other headers stands beside the case's own.
  - `match_request(manifest, case, request, *, expect=None)` checks the run scope (`in_scope`) first, then finds the plan step with the request's method, path and identity, refusing with `scope`, `step` or `identity`. Where several match, `expect` (the sealed step the caller is about to send) picks the one with its headers; still alike, the first wins: the plan lists the case's own request and controls before the engine's steps. `authorize`, the supervisor and the fixture sequence use it.
  - Also: `own_step(case, manifest=None)` is the case's own step; `read_only(case)` tells the worker whether the case changes state; `body_permitted(step)` tells whether a step may carry a body or be a write (a missing field says no); `CASE_PHASES` names the phases of the case's own request and controls. The controller reads `side_effects` and a fixture case's body rule from `own_step`.
  - Old runs: for a case without `request_plan`, `match_request` and `own_step(case, manifest)` work its plan out from its fields on the spot (the lifecycle from `allowed_requests`), unchecked and never written back, so neither its hash nor the approval changes; a worker given a case without a plan reads `read_only` by `designed_by`.
  - The transport's `adapters._prepare_request` reads the same header, vocabulary and path rules; the method list has one more copy each there, in `fixture_protocol`'s profile registration and in `tool_runners`' tool requests.
- worker_runtime/worker_entry: controller, independent trusted supervisor, isolated worker and Unix socket relay. Docker has no direct egress; process_test is explicitly unisolated, and a runtime profile can only select the Docker backend. The supervisor limits the worker to timeout_seconds from its start; the lease and the controller's result deadline also cover supervisor startup, the bounded container-create budget and teardown. Once the supervisor has started, any controller-side failure is outcome_unknown, never "nothing sent"; a malformed worker result is execution_error and keeps the supervisor's records, so a recorded leak still fails. Fields only the supervisor or controller set are dropped from the worker's JSON. One relayed request, broker lock to last byte, ends within 9 seconds, before the 10-second relay and tool clients give up, and the target receives the sealed body bytes. The Docker Engine API version is negotiated (1.44–1.52). The controller's result deadline covers the supervisor's bounded container-create budget plus teardown, so a slow daemon cannot invent an unknown outcome for a healthy worker.
- Before sending, the supervisor matches the request plan with `match_request`: it first binds the request to the spec's next step in order (`http_case` and `request_sequence`), then finds that step in the plan and reads its source and whether it may carry a body there; a request it cannot find is refused. A tool task sends only the case's own request and its positive controls. An `http_case` worker gets only the case's own step of the plan, to tell whether the case changes state; a `request_sequence` worker gets only the case id and each step's request, no plan; a tool task runs only operator-written cases and gets its spec as it is.
- lease: persistent capability binding, reservation ledger, renewal/expiry, unknown outcomes. Controller EOF or expiry revokes sockets before termination. Renewals run off the controller event loop; the worker guardian and controller heartbeat tolerate isolated transient lease-database errors (four renewals per TTL: two consecutive failures are tolerated and the third ends the worker) but fail closed immediately on real expiry or revocation.
- tool_runners: fixed input/argv compilation → isolated execution → bounded artifact collection → normalized observations → oracle over broker evidence. No arbitrary shell/scripts.
- fixture_protocol: hashed reviewed reset/setup/cleanup, session capture, administrator-registered generic profiles; built-ins are synthetic. `fixture_lifecycle` lists the steps the engine adds around a fixture case (id, phase, method, path, identity and fixed headers, no body), sealed into its request plan; before a sequence is sent, each of its steps is matched against the plan with `match_request`.
- effect_collector: independent sequenced events and sink receipts, HMAC-bound under a per-call key that exists only while the collector verifies them (stored bundles are evidence records, not re-verifiable signatures); target JSON cannot confer provenance.
- store/traceability: PostgreSQL production, SQLite demo, atomic job/run commits, versioned entities/evidence links; events live in their own append-only table (a save writes only the events not yet stored and the run body carries none), the progress stream reads only the events after its cursor, and the `/runs` inventory reads summaries alone.
- catalog: pinned canonical IDs, version/source checks; category membership is not test coverage or certification.
- settings: the backend process's VIBEAUDIT_* settings, read and checked in one place (startup token format and strength, data directory, database URL, console origins normalised to the form a browser sends, source roots, catalog and configuration paths); credential references are not settings and stay with adapters/providers/the supervisor, read by the names a run or profile gives.
- benchmark: seven comparative arms, common budgets/tool evidence, independent ground truth and incomplete accounting. Synthetic runs verify plumbing only.

## Roles and evidence

Live requires one commander and three distinct reviewer configurations/families. Optional dedicated architecture_mapper, challenger, threat_modeler and test_designer can use approved separate endpoints; otherwise the commander performs those roles. An optional fallback Agent lists the Agents it stands in for in `fallback_for`: it answers only when one of them refuses (refusal) or is truncated (truncated), and any other failure still stops the run. It is probed at preflight and charged to the same budget as any model; each answer it gives is recorded in the activity log and the report's capability limits, and a review records the model that actually wrote it (`answered_by`), so the family diversity gate checks that one. A reviewer's fallback must therefore be a family no other reviewer uses, and each Agent has at most one fallback. Reports verify existing evidence; an optional dedicated reporter may only reorder the exact existing finding IDs and cannot create claims. Models cannot add targets, run shell, change network policy or confirm findings by majority vote.

Reviewers receive the same core questions and snapshot without scanner findings or other reviewers' conclusions. Static scanners run concurrently but join only after the initial batch is sealed. Missing reviewers cannot produce a completed three-model review.

Cases bind threat model, requirement, source, fixture and case hashes. Controls and cleanup must also be in scope. A sealed case carries its request plan under the case hash: `authorize`, the supervisor and the fixture sequence then let through only the plan's steps. Deployment change requires a new run; unknown outcomes require reconciliation/reset.
